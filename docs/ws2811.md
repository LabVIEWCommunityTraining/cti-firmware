# WS2811 LEDs (Pico / Pico W / Pico 2 / Pico 2 W)

The **standard versioned CTI VISA firmware** includes both WS2811 and HUB75
support. Select a service through SCPI at runtime; neither claims PIO, DMA,
RAM or GPIOs at boot. There is no separate WS2811 UF2.
The platform implementations remain separate; this display service lives in
`platform\common\ws2811.cpp`, with its nine-instruction PIO program in
`platform\common\ws2811.pio`.

WS2811 is a serial, latched LED controller, not a multiplexed HUB75 panel.
After a frame and reset-low interval, its internal PWM retains the output
without continual host traffic or repeated PIO refresh. All eight bits per
RGB channel are transmitted. This is not the four-plane BCM used for HUB75.

## Wiring and scope

- Connect the selected GPIO to the **DIN** end of the chain, with common ground.
- Use a suitable level shifter: the original WS2811 specifies VIH >= 0.7*VDD,
  so 3.3 V GPIO is not guaranteed to drive a 5 V input reliably.
- Power the LEDs externally at their rated voltage; never power them from a GPIO,
  and never connect strip supply voltage to a Pico pin.
- A data pull-down keeps DIN low while the firmware pin is disconnected.
- Count **addressable WS2811 controllers**, not necessarily physical LEDs.
  Common 12 V strips have three physical LEDs per independently controlled pixel.
- This implements three-channel WS2811 signaling, not RGBW or clocked strips.

One chain is supported, with 1..4096 addressable pixels. Allowed data GPIOs
are the exposed header pins 0..22 and 26..28. Defaults: 64 pixels, GP2,
800000 bits/s, RGB wire order, 400 us reset low, and 25% brightness on START.
Select 400000 bits/s if required by the device's speed selection; a command
does not change the chip's hardware mode. RGB is the original WS2811 order;
all six channel permutations are available for differently wired products.

## Commands

Send one command per LF-terminated message; CRLF is accepted. Reads are needed
only for queries ending in `?`. Check `SYST:ERR?` after setup and each upload.

| Command | Behavior |
|---|---|
| `DISPlay:WS2811:COUNt <n>` / `COUNt?` | Set/query 1..4096 addressable pixels, while stopped. |
| `DISPlay:WS2811:PIN <gpio>` / `PIN?` | Set/query data GPIO, while stopped. |
| `DISPlay:WS2811:RATE <bitsPerSecond>` / `RATE?` | While stopped, select the legacy 400000 or 800000 timing shortcut, resetting all pulse timings and reset low to 400 us. Query returns the integer worst-case bit rate of the current timing, which can differ after TIMING. |
| `DISPlay:WS2811:TIMing <T0H_ns>,<T0L_ns>,<T1H_ns>,<T1L_ns>,<RESET_us>` / `TIMing?` | Set explicit positive integer timings while stopped. Pulse widths are quantized to 62.5 ns ticks. Query returns effective widths rounded to the nearest whole ns, followed by reset us. |
| `DISPlay:WS2811:ORDer <order>` / `ORDer?` | Set/query RGB, RBG, GRB, GBR, BRG or BGR wire order, while stopped. |
| `DISPlay:WS2811:START` | Allocate buffers, claim one PIO state machine/nine instructions and one DMA channel, load the bundled program with the selected instruction delays, and asynchronously transmit black at 25% brightness. Repeated START while running is a no-op. |
| `DISPlay:WS2811:DATA <offset>,#<digits><length><bytes>` | Stage 1..2000 raw RGB888 bytes. Offsets are bytes, not pixels; start at zero and continue contiguously. |
| `DISPlay:WS2811:SHOW` | Queue transmission of a complete `count*3`-byte frame. Rejects incomplete frames or a pending transmission/reset. Clears received count on acceptance. |
| `DISPlay:WS2811:BRIGhtness <percent>` | Integer 0..100. Retransmit the retained frame with scaled brightness; no DATA or SHOW needed. Requires running with no pending transmission. Does not disturb a partial next-frame upload. |
| `DISPlay:WS2811:STATus?` | `running,received,pending,brightness,frames`, five comma-separated integers followed by LF. |
| `DISPlay:WS2811:STOP` | Hold DIN low during bounded DMA shutdown, unload PIO, release resources and disconnect the GPIO. Does not send black; LEDs can retain their previously latched color. Repeated STOP is safe. |
| `*RST` | Also stops both display services; does not transmit a WS2811 black frame. |

Configuration survives STOP and `*RST`, but not reboot. Configuration setters
are locked while running or while failed shutdown retains resources.
START resets the completed-transmission counter and brightness.
`pending=1` includes the initial/reset wait, DMA transmission and final
FIFO/OSR drain plus latch time. Poll until zero before SHOW or brightness.
`frames` counts completed transmissions, including initial black and brightness
updates; it does not continually increase when the LEDs simply hold an image.

The incoming image is always **R,G,B bytes for each pixel**, first controller
first, even when ORD selects a different on-wire order. No image header,
compression, RGB332, gamma correction or RGBW is accepted. Brightness scales
each original channel to the nearest integer using `(value*percent+50)/100`;
retaining the original frame avoids cumulative dimming.

DATA never alters the active DMA buffer. You can stage the next frame while
one is transmitting, but SHOW and brightness must wait for pending=0.
Offset zero restarts staging; other gaps/overlaps, oversized chunks and
out-of-bounds writes report -222 without changing staging. Embedded NUL, LF,
CR, comma, `#` and 0xFF are valid payload bytes. Block lengths must exactly
match the bytes sent; see [binary block framing](hub75.md#commands).

### Complete copy/paste test: four pixels

This uses only printable ASCII payload bytes and therefore produces modest
red-, green- and blue-dominant pixels plus gray, not pure RGB primaries.
It assumes GP2 is unused.

Send these setup commands, then read the status response:

```text
DISP:WS2811:STOP
DISP:WS2811:COUNT 4
DISP:WS2811:PIN 2
DISP:WS2811:RATE 800000
DISP:WS2811:ORD RGB
DISP:WS2811:START
SYST:ERR?
DISP:WS2811:STAT?
```

Wait/poll `DISP:WS2811:STAT?` until its third field is zero. Then:

```text
DISP:WS2811:DATA 0,#212@!!!@!!!@@@@
DISP:WS2811:SHOW
SYST:ERR?
```

The payload is exactly 12 bytes, representing four RGB pixels:
`@!!`, `!@!`, `!!@`, `@@@`. Send the characters literally with no quotes.
For pure red/green/blue/white use binary bytes
`FF 00 00 00 FF 00 00 00 FF FF FF FF` instead of those twelve ASCII characters.

To turn the LEDs off, first wait for pending=0, then send:

```text
DISP:WS2811:BRIG 0
```

Wait for pending=0 again **before** STOP. STOP alone does not erase the chip's
latched output. On an error or interrupted transmission some LEDs may have
partially updated; DIN low is not an electrical power-off mechanism.

### Host-generated known pattern

With Python and pyserial available:

```powershell
python tools\ws2811_smoke.py --port COM7 --count 64 --pin 2 --brightness 25
python tools\ws2811_smoke.py --port COM7 --count 64 --pin 2 --rate 400000 --order GRB
python tools\ws2811_smoke.py --port COM7 --count 64 --pin 2 --timing 500 2000 1200 1300 500
```

The tool configures the service, waits for initial black/reset completion,
uploads a repeating pure red/green/blue/white RGB888 pattern, checks errors,
and waits for the final latch. It leaves the image latched after exiting.
It does not measure optical brightness, verify wiring, or prove chip compatibility.

## Timing, memory and resource ownership

The PIO program is compatible with PIO version 0 on both Pico chips.
It shifts MSB-first with 24-bit autopull from left-aligned 32-bit words.
DMA feeds the joined eight-word TX FIFO; there is no per-bit CPU work or
DMA IRQ handler. The existing main loop polls a bounded state machine.

The clock divider always targets **16 MHz**, or 62.5 ns per PIO cycle.
RATE is a compatibility shortcut for these timing sets; either selects
400 us reset low:

| Rate | Bit period | Zero high / low | One high / low |
|---|---|---|---|
| 800000 | 1.25 us | 0.25 / 1.00 us | 0.625 / 0.625 us |
| 400000 | 2.50 us | 0.50 / 2.00 us | 1.250 / 1.250 us |

RATE shortcuts retain the previous nominal pulse widths. For other devices,
set explicit values from the actual supplier's datasheet:

```text
DISP:WS2811:STOP
DISP:WS2811:TIMING 500,2000,1200,1300,500
DISP:WS2811:TIMING?
```

The response is `500,2000,1188,1313,500`: the requested 1200 and 1300 ns
widths become 19 and 21 ticks (1187.5 and 1312.5 ns). Query values are rounded
half-up to whole ns for display and can be sent back without changing the
selected tick counts. Values are not silently clamped.

After quantization, accepted bounds are:

| Duration | Allowed PIO cycles |
|---|---|
| Zero high, T0H | 1..16 |
| One high minus zero high, T1H-T0H | 1..16; a one must have a longer high pulse |
| Zero low, T0L | 4..49 |
| One low, T1L | 4..49 |
| Reset low | 50..100000 us, integer |

This permits independent zero/one low durations and different bit periods.
Unsupported timing, missing/extra parameters or changes while running report
SCPI errors and preserve the previous configuration. TIMING supersedes the
RATE shortcut; a subsequent RATE replaces the custom timing. There are no
named chip profiles. Color order remains independent.

The bundled program's opcodes, side-set levels and branch targets are fixed;
START patches only its delay fields before loading it into claimed PIO memory.
The low interval includes the following iteration's one-cycle OUT. FIFO
starvation therefore remains low for either bit value.

Check the exact chip revision. Fractional PIO dividers introduce
system-clock-scale variation; the default Pico clocks give an exact average
16 MHz, not necessarily equal individual cycle lengths. The
[older WS2811 timing reference](https://www.kynix.com/components/WS2811-3-Output-Channels-Special-for-LED-Driver-Circuit-.html)
specifies >50 us reset, while Worldsemi's
[newer English document](https://www.world-semi.com/downloads/datasheets/en/ws2811-2.5.pdf)
specifies >280 us and its
[Chinese document](https://www.world-semi.com/downloads/datasheets/zh-CN/ws2811-2.5.pdf)
specifies at least 350 us. These documents differ and must not be assumed
interchangeable. The default reset is now **400 us**, rather than 300 us.
Custom timings are not a guarantee of chip compatibility.

Firmware first waits the selected reset interval before a transfer, then after
DMA completion allows nine words' worst-case wire time (eight FIFO plus one
OSR), using the longer of the zero/one periods, plus another selected reset
interval before marking pending=0.
Polling can delay completion reporting, never shorten that minimum.
An empty FIFO stalls with DIN low; sustained bus starvation can latch a
partial frame and is not guaranteed to preserve its intended contents.

With RATE shortcuts, payload transmission takes `count*30 us` at 800 kbit/s
or `count*60 us` at 400 kbit/s, plus reset/drain margins, polling and host
overhead. At 4096 pixels this is 122.88 / 245.76 ms of wire time. Custom
timing uses `count*24*max(T0H+T0L,T1H+T1L)` as its conservative wire-time
budget. RATE? reports 16 MHz divided by that maximum bit-cycle count,
rounded down to an integer, not a separate clock setting.

Buffers use `count*10` bytes: RGB upload (3), retained original RGB (3),
and DMA word (4) per pixel, plus object/allocator overhead. Maximum is
40960 bytes of pixel storage. No allocation occurs until START.

HUB75 and WS2811 may run together on **disjoint pins**, subject to available
PIO instruction slots/state machines, DMA and RAM. Their pin guards reject
conflicting digital, PWM, ADC-enable, peripheral-init or display START commands.
The normal CTI blocking peripheral commands are unchanged and can delay status
polling, but DMA continues to transmit without CPU bit timing.

Allocation/PIO/DMA failures report -225; configuration/state conflicts -221;
range/upload errors -222. Shutdown requests DMA abort with a 1 ms bound.
If abort does not finish, DIN is forced low and the DMA buffer/resources stay
reserved until the main loop can safely clean them up. A DMA bus error or busy
transfer exceeding the configured worst-case wire time plus 100 ms stops the service with -200.
Idle, correctly latched LEDs do not trigger the timeout.

## Firmware and verification

Use the standard build instructions for [RP2040](../platform/rp2040/readme.md)
or [RP2350](../platform/rp2350/readme.md). Outputs are:

```text
uf2\cti_visa_rp2040_pico_0.9.4.uf2
uf2\cti_visa_rp2040_pico_w_0.9.4.uf2
uf2\cti_visa_rp2350_pico2_0.9.4.uf2
uf2\cti_visa_rp2350_pico2_w_0.9.4.uf2
```

Choose by board, not by display type. Old display-specific artifact names
are not generated by new builds.

Native tests run both chip configurations, exercise parser/packing/brightness,
all color orders, bounds, allocation/resource failures, shutdown, staged
uploads and HUB75 coexistence. Python tests assemble the actual PIO-v0 program
and verify all byte values, MSB-first ordering, bit periods/high pulses and
low output on FIFO starvation. Actual C++ delay patches are modeled at
both RATE shortcuts, custom unequal bit periods and timing bounds. Native
tests cover quantization/query round trips, rejected changes, reset waits
and custom DMA timeout/drain budgets; host tests cover explicit timing uploads.
There has been **no WS2811 physical-strip or logic-analyzer validation**.
